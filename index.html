WhatsApp bot — simple how to do

What it does, how to use it, and how it was built — in about five minutes.

AS-Sur sits in the cohort's WhatsApp group and answers questions about logistics: pass marks, retake rules, deadlines, lecture links, which file is where. Everything it says comes from the Physicianeers 2026 hub and nowhere else. It is not a general-purpose chatbot: if the hub does not contain the answer, it tells you that instead of inventing one.

How to use it

Three ways to summon it, inside the cohort's group:

  • Start your message with ?sur followed by your question — for example: ?sur what is the pass mark for the subject?
  • @mention the bot in your message and ask
  • Or reply to any one of its own messages

It answers in whichever language you asked in: ask in Arabic and it replies in Arabic, ask in English and it replies in English.

Most importantly, it answers from the hub only. If something is not written there, it tells you plainly that it cannot find it and points you to your representative or the site — it does not guess and it does not invent.

It never speaks unless summoned. Everything else in the group it does not read and does not reply to, and it never replies in direct messages at all.

In short: start with ?sur, @mention it, or reply to it.

One small program, always running, doing four jobs. No magic anywhere in it.

1. Reading the hub's data

The hub keeps its content in Firestore — a hosted database that a website can read directly from the browser. Because the hub's content is public, the bot can read the same data over ordinary web requests with no password, exactly as a visitor's browser does. It pulls ten collections (announcements, exams, answered questions, files, deadlines, lecture schedule, and so on) and flattens them into one long labelled text document — we call it the digest. Every line carries its source, e.g. [EXAM RULES] Pass mark: 70.

Some of the hub's content is not in the database at all — the exam rules and the meeting-notes Q&A are written directly into the page — so the bot also fetches the page itself and reads those out of it.

2. Asking Gemini, with the data attached

The digest is small enough to hand the model in full. So on every question the bot sends Gemini two things: the whole digest, and the student's question — plus firm instructions to answer only from the digest and to reply with the exact word NO_ANSWER if the answer is not in there. The temperature is set to 0, which means "be as deterministic as you can, do not be creative".

3. Listening on WhatsApp

WhatsApp has an official business interface, but it does not support group chats at all. Group participation is only possible by connecting as a linked device, the same way WhatsApp Web does — which is against WhatsApp's terms of service, and the account can be banned for it. That is a real trade-off, taken knowingly: the bot therefore runs on a dedicated spare number, never anyone's personal one, and it never messages anybody first.

Because it keeps a live connection open, it needs a machine that is always on. It runs as a small always-on service on a cloud server with automatic restart.

4. Deciding when to speak

This is the part most of the care went into. In a group of ~166 people, the failure that gets a bot thrown out is not a wrong answer — it is noise. So the rule is written to fail closed: anything the code cannot prove is a summons results in silence. Wrong group, no summons, an empty question, the bot's own messages, direct messages, someone's @everyone broadcast that happens to tag the bot along with everybody else — all silence. There are also limits: at most one reply per message, one reply per person every 10 seconds, and 30 per group per hour. When it hits a limit it goes quiet rather than announcing it.

Simple code

Three ideas, simplified for reading. The real code has error handling, caching and tests around each of these; the shape below is honest, but it is not copy-paste ready.

Reading a database collection over plain HTTP

const base = "https://firestore.googleapis.com/v1";
const project = "mtc-qa-hub";

async function readCollection(name) {
  const url = `${base}/projects/${project}/databases/(default)/documents/${name}`;
  const response = await fetch(url);
  const data = await response.json();
  return data.documents ?? [];
}

// announcements, exams, questions, files, deadlines, schedule, ...

No SDK, no credentials — the data is public, so it is just a URL.

The instruction that keeps it honest

const instructions = `
Answer ONLY from the CONTENT below. Never use outside knowledge.
Never guess. Never invent a rule, date, grade, or policy.
If the CONTENT does not clearly answer the question,
reply with exactly: NO_ANSWER

Mirror the user's language: Arabic question, Arabic answer.
Be brief - this is WhatsApp, not an essay. Maximum 3 short lines.

CONTENT:
${digest}`;

If the reply is NO_ANSWER, the bot never shows that word to students — it swaps it for the bilingual "I can't find this, ask your rep or check the site".

Deciding whether it was summoned

function isSummoned(message) {
  if (message.fromMe) return false;                    // never itself
  if (!message.chatId.endsWith("@g.us")) return false;  // groups only
  if (!allowedGroups.includes(message.chatId)) return false;  // ours only

  return message.text.startsWith("?sur")        // the prefix
    || message.mentionedIds.includes(botId)     // an @mention
    || message.isReplyToBot;                    // a reply to it
}
// anything else: stay silent, and do not even log it

Three things we learned

Not every AI app needs a vector database

The standard advice is to chop your documents up, turn each piece into numbers ("embeddings"), store them in a special database, and at question time retrieve only the pieces that look relevant. That is called RAG, and it exists because models can only read so much text at once.

We measured the hub first: 86 documents, about 86 KB of text — roughly 15,000 tokens (a token is a chunk of a word; the model's reading limit is counted in these). That fits comfortably in a single request. So there is no vector database, no embeddings and no chunking here: the entire knowledge base is sent with every single question. The model sees everything, every time, so nothing can be missed by a bad retrieval step — and there is a whole moving part that simply does not exist and therefore cannot break. Measure before you architect.

Waiting for changes beat asking for them — cheaper and fresher

The first version re-read the whole hub every 10 minutes. That is roughly 12,800 database reads a day, and an answer could still be up to 10 minutes out of date.

Switching to real-time listeners — where the database pushes a notification when something actually changes, instead of the bot repeatedly asking — cost about 100 reads a day with effectively no staleness. Both numbers moved the right way at once, because reads are billed only for documents that really change, and an idle database costs nothing. It mattered for more than money: those reads come from the same free quota the students' own website depends on, so a chatty bot would have degraded the site it serves. (A slow re-read still runs a few times a day, purely as a safety net in case a listener dies quietly.)

Refusing to answer is a feature, not a failure

The content here is exam rules and programme policy. A confidently wrong answer about a pass mark is far more damaging than no answer at all — a student can act on "I don't know, ask your rep"; they cannot recover from a made-up retake rule. So refusal was designed in from the start, tested for deliberately, and it is why the prompt has that NO_ANSWER escape hatch. The refusal message and the "something broke technically" message are also kept as two different sentences, because they ask the student to do two different things.

A bonus lesson in looking before assuming. A student asked for a lecture link and the bot said it could not find it — even though the link was plainly visible on the hub. It turned out the lecture and lab links were hardcoded inside the page's own JavaScript, not stored in the database the admin screen writes to. The bot was reading the database and the links were never there. Your data is where it actually is, not where the architecture diagram says it should be.

What it cannot do

  • It knows only what the hub publishes. If the hub is silent or out of date, so is the bot.
  • It will decline anything else — medical questions, study advice, general knowledge, opinions. It has no policy of its own and will not offer one.
  • It cannot see the whole conversation. Each question is answered on its own, with no memory of what came before.
  • It never starts a conversation, never sends direct messages, and only reads the messages that summon it. Everything else in the group is ignored and never leaves the program.
